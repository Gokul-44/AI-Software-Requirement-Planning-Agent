# Project Status: AI Software Requirement & Planning Agent

_Last updated: 2026-11-14_

## Objective

Build and deploy a web system that takes a one-line software idea and returns a traceable, schedule-consistent plan:

- requirements (functional and non-functional)
- epics
- user stories with acceptance criteria
- tasks
- estimates
- a validated dependency graph
- a critical path
- a capacity-feasible sprint plan
- a grounded risk register

The plan exports to Jira CSV and Markdown. Design principle: **AI generates, algorithms verify.**

The API can already resume from the failed stage (`apps/api/src/app.ts:224-276` accepts `from_stage = completed + 1` and copies stages 1-2), but the UI never offers it. Fix: (a) `apps/web/src/pages/RunProgress.tsx:228`: `const detailCode = typeof data.error?.details?.code === 'string' ? data.error.details.code : null; const stageError = data.error ? friendlyCode(detailCode === 'QUOTA_EXHAUSTED' ? 'QUOTA_EXHAUSTED' : data.error.code) : null;` (b) `apps/web/src/lib/friendlyError.ts`: add `'QUOTA_EXHAUSTED'` to `GOLDEN_CODES` (line 12) and add `QUOTA_EXHAUSTED: { title: 'The free AI quota is used up', message: 'The free language-model quota for today is used up, so this stage could not run. Try again later, or open a golden demo plan to see a finished plan now.', offerGolden: true }`. (c) `RunProgress.tsx:403-406`: for quota errors hide "Start a new run". For other stage failures add "Retry from stage N" (`useRerun(runId).mutate({ from_stage: data.error.stage })`, then go to the new run's page). (d) Optional, API: keep a `quotaExhaustedUntil` timestamp in the pipeline when the harness reports `QUOTA_EXHAUSTED` (daily quota, `gemini.ts:216`). While it is set, `guardNewRun` in `app.ts` answers 429 `BUDGET_EXHAUSTED`, so no new run starts only to fail. Add a test for each of (a) to (c).

5. **The capacity ratio has three different values on one plan: 1.5x, 1.54x and 1.55x.** `apps/web/src/pages/plan/OverviewTab.tsx:28-30` computes it from rounded days (30 / 19.5 = 1.54) and line 185 prints it with `toFixed(1)` ("1.5x"). Update the signal test.
6. **`sprint_overload` is almost always true, so it produces a "high" risk that the packing itself causes.** Greedy packing fills every sprint up to C by design. The real run got 3 `sprint_overload` signals (two high, including the last sprint) and the high risk RK-002 "Severe sprint capacity saturation across all sprints". An examiner will ask why the algorithm reports its own output as a high risk. Fix (`packages/scheduler/src/signals.ts:161-185`): emit at most ONE `sprint_overload` signal for the sprints at or above `overloadHigh`. Its message is "N of M sprints are packed to at least 98% of capacity, so there is no buffer for estimation error", and its `task_ids` are the critical tasks in those sprints. Severity is `medium` when every sprint is full, otherwise `low`, never `high`. Update the B5 table and the signal tests.
7. **Stage 3 leaves out the core data model and the "place order" step.** In the real plan the `database` layer is 5 of 119 points (only the user, address and review tables). The story for the core workflow must include the endpoint that creates its main record (for example 'Implement place-order endpoint')."
